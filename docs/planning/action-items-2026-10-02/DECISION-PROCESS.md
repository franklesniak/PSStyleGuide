# Finding-specific decision process

Use the owner's process for every distinct material finding or design decision. Complete the steps in order before the corresponding implementation. A duplicate report can link to an existing decision after confirming the same facts. Mechanical execution of a selected solution does not need a new decision. Do not post comments or other external messages unless task execution and its scope authorize that publication.

1. **Validate.** Reproduce the defect or show the material improvement. Name the affected current consumer, actual failure, evidence and limits. For alleged paperwork, compare concrete benefit to ongoing maintenance, reviewer attention, token/runtime cost and failure/restart complexity. Neither line count nor a merged retirement proves low value.

   **Materiality and record size.** Use the full seven-step process for a finding that changes product behavior, security properties, policy text, a public interface or contract, a settings proposal, or any reviewer finding on product code. For a test-fixture, scratch-setup, formatting, lint, environment or tooling-availability defect that changes neither production code nor guide text, use a short note of at most five lines: what failed, root cause, fix, test and link.

   Keep one canonical record per finding in the owning task's results folder; duplicate reports link to it. PR replies contain a link plus at most three lines. Do not add a post-decision guide-contract audit unless the decision changes guide or instruction text. Record model-routing limitations once in ROUTING-AND-PARALLELISM, not in every result. The coordinator samples worker hashes and score totals; the independent final-quality reader checks integrity at PR level. Two full pre-commit passes are required only where an issue's own acceptance criteria require them (PS175); otherwise one pass on final bytes is sufficient.

2. **Identify all relevant stakeholders.** Tailor the list to the finding. Consider the owner; both maintainers; experienced and new contributors; PowerShell/Terraform users; documentation authors and readers; generated-artifact consumers; local/remote agents and their operator; code and independent-quality reviewers; CI, release, DevOps and platform engineers; dependency maintainers; Windows/Linux/Bash/PowerShell users; security executives accountable for risk; application, infrastructure and supply-chain security engineers; privacy/data owners; cloud/backend administrators; incident and recovery operators; auditors/history custodians; directors of user experience; QA analysts; accessibility/localization users where affected; and business/cost/schedule stakeholders. Include other affected roles. Explain omitted categories when their absence could change the decision. Do not reuse a generic stakeholder list without checking it. Apply these perspectives to both the options and the finding-specific rubric. Check the steps a new user must perform, the chance of user error, reproducibility, negative controls, and the difference between proposed and executed tests where relevant.
3. **List options before proceeding.** Include no change, removal, a smaller control, repair, native/reused tools, factoring shared code with configuration, targeted exception and deferral where reasonable. Consider combinations and perspectives across those stakeholders. Be exhaustive within the actual supported problem; explain which combinations collapse into another option or fail a hard constraint. Do primary-source research when correctness depends on external behavior.
4. **Describe a new rubric before scoring.** Define each criterion, weight and score meaning for this finding. Favor technical correctness, real safety, reliable recovery and legitimate usability. Give churn, implementation difficulty and original-scope convenience lower weights. State hard constraints that a high score cannot waive.
5. **Show the scores before choosing.** Use a table with every option, criterion score, weighted total and key uncertainty. Check arithmetic. Explain why the winner clears the hard constraints; do not use an invented number as empirical evidence.
6. **State the selected solution.** Follow ASD-STE100 for the selected-solution instructions: short direct sentences, one action per instruction, consistent technical names, explicit conditions and limits. Give enough context for a new reader. Check the applicable writing rules and controlled vocabulary; plain wording alone does not establish compliance. Do not claim formal dictionary compliance without an actual check. Include primary references and relevant test environment, commands, native results and limits.
7. **Implement and verify.** Make the selected change, run meaningful validation and report its result. If new evidence invalidates the selection, revise that same decision and re-evaluate before further edits. Retain one complete record and link duplicate reports; do not produce per-command rubrics or completion-only copies.

Store each canonical decision in the owning task's results folder. The PR body carries its reviewer-facing decision summary; a planning-branch link is supporting evidence because that branch never merges. The PR-owning worker drafts the decision and implements after selection; coordinator review occurs at round boundaries. Publication before each edit is not required. Do not create a separate permission ledger. Real human authority and operational approvals remain distinct from an agent's recommendation or score table.
