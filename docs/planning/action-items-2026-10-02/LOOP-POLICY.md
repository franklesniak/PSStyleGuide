# Implementation, review and paired convergence

This is the single current lifecycle policy for A00–A21. Repository instructions and actual owner authority still govern their scopes. [STATUS.md](STATUS.md) holds progress; archived task bodies and old TEMP state do not select current work.

## Owner CI direction, 2026-10-06

Do not merge a PR while CI is failing. A CI relaunch is permitted at most once per hour for that PR; record the last relaunch timestamp and reconcile the accepted request before another attempt. Do not create scheduled retries without an explicit request. If a PR was merged with failing CI, pause project work and report the native status to the owner for triage. Do not treat a service disposition or a valid fallback review as proof that a cancelled or failed workflow passed. The current owner hold and its exact scope are recorded in [the audit](results/owner-ci-audit-2026-10-06/REPORT.md). This owner direction takes precedence over earlier lifecycle interpretations.

## One outcome, two loops

| Limit | Counted unit | Stop condition | Reset rule |
| --- | --- | --- | --- |
| One PR review | A round starts when its first required reviewer request is issued for the reviewed input; it includes the Copilot and Codex results and disposition of their findings | Both reviewers clean on the same current input, **80 rounds**, or **8 elapsed days** from first issued request, whichever occurs first | Never reset for new head/body, rebase, reviewer retry, agent, chat, failure, pause or restart |
| One work item's repository transfers | Initial implementation is 0; each later repair batch that changes destination to the other repository is +1 | Verified paired convergence, or declared cap: **8 narrow / 12 coupled / 16 justified large** | Never reset for a new PR, agent, issue title, split performed to evade the cap, or restart |

Days are 24-hour elapsed periods, measured from persisted UTC timestamps, including wait time. At startup and before each request, compare current time to the fixed deadline. For a resumed PR, recover its first request and round history; do not create a new clock. A service retry for the same input stays inside its round, is recorded, and has the separate finite limit below. A round with failed or missing review is not a clean round. A clean result from an old head cannot pair with a new-head result.

A transfer is one direction, not a round trip: PS initial delivery = 0, TF counterpart = 1, PS feedback repair = 2, TF follow-up = 3. A diff that proves no change does not consume a transfer. Additional same-repository repair PRs do not add a transfer but retain their history and cannot evade a PR's limit by replacing that PR. A replacement PR for the same unresolved candidate inherits the earlier first-request clock and consumed rounds; a genuinely separate independent outcome must be defined before work, with a reason other than a spent limit.

Declare the transfer cap at task start. Narrow means one behavioral objective and a small independent surface; coupled means multiple consumers/security boundaries; large means a cohesive change that cannot safely be split. Task caps are maximums, not iteration targets. Do not enlarge a cap silently after spending it. Reserve the final two transfer slots for bug repair and byte alignment. At that point, freeze optional redesign and preference changes.

## Delivery and convergence sequence

1. Read the task, live issues, applicable instructions and actual predecessor results. Identify what already exists. Complete only missing work. Classify retired requirements through the merits review, not by age or line count.
2. Pin native main and choose one source repository. Use its own isolated clean worktree and focused `codex/` branch. Keep the planning branch and other workers' files out. Give one worker ownership of the exact paths and coupled contracts. Verify needed protected-file authority and installation feasibility early.
3. Implement one focused outcome. For each confirmed finding, finish the [decision process](DECISION-PROCESS.md) before the corresponding edit. Run meaningful affected tests; reuse unchanged evidence. Do not add tests that merely duplicate the implementation or receipts that repeat Git facts.
4. Publish an accurate issue/PR with the concrete problem, behavior, validation and material limits. Use the normal non-force path. For an externally visible mutation, verify the affected preimage immediately before it and read back the affected native object once afterward. Do not repeat a write because local recording failed.
5. Run the PR review loop below. After applicable findings are resolved, obtain fresh independent final quality for the actual candidate. It must inspect diff, test relevance, scope, security and pair implications; a second copy of the same review is insufficient. Record actual reviewer identity and capabilities.
6. Recheck actual head, base, checks, mergeability, required approval and scope immediately before the on-plan merge. If the base changed, assess its effect and rerun invalidated validation/review; do not reuse stale acceptance. Use an allowed normal merge method with no override. Read back merged commit/tree and relevant landed CI/service behavior. A merge alone does not prove deployed acceptance.
7. Compare the delivered paths and all coupled common contracts to the peer's current main. Compare raw Git blobs and modes, including missing/renamed files and affected generated outputs. For a genuine language-only change, prove the peer has no applicable shared delta; do not manufacture a counterpart PR.
8. If a useful common difference remains, increment the transfer count **before** starting that destination repair. Carry the accepted source identity, relevant decision and validation into a focused peer PR. Repeat steps 2â€“7. Review-driven improvements in the peer must be checked back against the first repository. Never declare completion after a one-way port alone.
9. End this outcome only on verified equality plus justified exceptions, or a truthful cap/blocker result. Store one final task result. A18 later repeats the full-tree audit so task-local comparisons cannot conceal drift elsewhere.

No simultaneous source/peer implementations of the same outcome. Read-only counterpart analysis may run during review. Different independent outcomes may run in parallel under the ownership rules; rebase and revalidate affected inputs before integration.

Track the relevant code, caller, threat-model and settings assumptions of completed conditional/no-change decisions. After a merge or settings change, reopen only the decisions whose inputs were invalidated, including previously completed A12/A13/A14 assessments. Preserve the historical result and spent budgets. A18/A19 must verify that every retained conditional result still applies to the final inputs; task order alone does not keep it valid.

## PR reviewer protocol

The two code reviewers are GitHub Copilot and remote Codex. A local worker is not the remote Codex reviewer. Keep a separate independent final-quality gate. An unavailable service or unavailable model is not a clean result.

1. Before a request, save the actual head, material review-facing scope and first-request time/round. Capture authenticated baselines for request events, requested reviewers, submitted reviews, review runs and relevant result comments. Use complete pagination on the surfaces required to attribute a result. Keep only the needed native IDs and timestamps in the pending task record.
2. Follow `AGENTS.md`: open the PR's GitHub Reviewers control, select **Balanced** for Copilot and submit once. Confirm a new authenticated request event or exact-head Copilot run. Record the effort observed in the timeline/overview when it completes. Do not infer Balanced from identity or HTTP201. If the supported interface cannot select it, record why and use `gh pr edit PR-NUMBER --add-reviewer '@copilot'`. REST fallback uses `copilot-pull-request-reviewer[bot]`. A resulting Lite review is valid; do not request another review solely to change effort. Never retain browser cookies, tokens or internal form data.
3. After Copilot's request is confirmed (or an actual scoped authority supplies a truthful terminal service disposition), issue the remote Codex review trigger once. Attribute its result through authenticated author, request time, baseline exclusion and exact reviewed input. A headless conversation response requires those causal links; ordinary comments or executor assertions are insufficient.
4. Do not duplicate a pending or possibly accepted request. A transport timeout is ambiguous, not failure. Reconcile native request events, requested reviewers, submitted reviews and exact-head workflow runs. Only complete negative readback after at least 120 seconds can prove no effect and permit one transport retry. A second proved no-effect result exhausts that request surface. Any readback with missing pagination or unavailable collections remains ambiguous.
5. A confirmed terminal service failure is distinct from no effect. Preserve its authenticated status and cause; do not require a brittle exact error string. Allow at most three channel attempts for that input, at least 60 seconds apart, within the same PR round and deadline. Do not start a new round solely to evade this retry limit. After exhaustion, use only an actual applicable owner-authorized substitute or record waiting_external/required owner action. Keep service failure and substitute results separate; do not relabel them clean. Do not copy an old grant unless its scope still applies.
6. Read all review findings, validate each and apply the full decision process once per distinct confirmed finding. Link duplicate reports to the existing decision after checking applicability. Repair material findings and run affected tests. A changed head, reviewed diff or material body scope requires a new round and new current-input results. Correcting a fact in local state does not require another review.
7. End normally when both reviewers are clean for the same current input and no material finding is open. Then run the final-quality and merge-readiness steps. Counters and request history remain recorded even if a prior input returns later. Never attribute one native result to two separate requests or inputs.

Serialize request sets across changed inputs. If one reviewer returns a finding while the other issued request is pending, safe local repair and validation can proceed. Do not request a new-input pair until each issued old-input request is authenticated terminal or has an applicable terminal reconciliation/disposition. Retain pending requests and their input attribution. Record supersession without calling the old input clean; never reuse an old result for changed bytes. The PR clock and round history continue during this wait.

One reply per thread per round is permitted, at most three lines plus a decision link. The PR body carries the decision summary. Planning-branch links are supporting evidence, not the record of truth, because that branch is never merged. The PR owner drafts and implements decisions; the coordinator reviews at round boundaries and owns native operations, STATUS and counters. Do not require publication of each decision before each edit.

Wait in bounded intervals; perform independent safe work while external results are pending. Do not poll unchanged state continuously. Save pending input and next action before leaving the active session. Future scheduled wakeups require a user request; this plan alone does not create an automation.

## What happens at a limit

At PR round80 or the eight-day deadline, send no further optional review requests for that PR. Collect already-issued results without duplicate triggers and record `review-limit-reached`, the actual clean/non-clean results and unresolved findings. Do not replace the PR to restart the loop. Complete deterministic local repair, validation and independent final quality where useful; a changed candidate still needs whatever review the repository actually requires. If that review cannot be obtained inside the limit, stop at the exact blocked merge gate.

At the transfer cap, complete and merge the last allowed focused repair **when required checks/review and final quality permit it**, then compare back. Do not begin transfer cap+1. A proved false-positive or nonmaterial suggestion can receive a documented no-change decision; do not repeatedly redesign for preference. If bytes still differ for no necessary reason, a material defect remains, CI is red or required approval is missing, mark `convergence-blocked`. Preserve the ready work and a concrete bounded next decision. Do not automatically approve a scope reduction or claim success. The user may choose a specific extension or changed scope after reviewing that result.

This is the owner's requested finite loop, not permission to bypass repository controls. `Accepted at limit` is a truthful distinct disposition only when the remaining feedback is resolved or explicitly nonmaterial, independent quality and all required gates pass, and the final paired result is verified. It is never called `both reviewers clean` unless both actually were clean.

When a PR reaches round80 or its eight-day deadline, the coordinator records a dated owner decision with exactly one value: `extend once by N days` (N stated), `accept at limit`, or `close`. Waiting on the owner's own pending authority is a valid reason to request an extension. No silent extension is permitted. An extension changes only the authorized deadline; it does not reset rounds, the original clock or transfers. Do not invent a decision while the owner has not answered. Required quality and merge gates still apply to acceptance at limit.

## Exact byte comparison and necessary exceptions

Use Git blobs from named native commits, not checkout text, CRLF-normalized diffs or hashes of generated summaries. Enumerate the complete path union and compare modes/type as well as bytes. For submodules, use the pinned gitlink identity and inspect required content separately. For a renamed counterpart, name both paths. A missing required path in both trees is a missing capability until a justified retirement proves otherwise.

For each actual exception, keep one entry in the owning task result and final comparison with: PS/TF paths and commits/blobs; exact differing region or whole-file language scope; the supported use that requires it; why one identical common implementation plus narrow configuration is insufficient; the finding decision; and the test/inspection proving the boundary. Mixed files must retain identical shared regions. No wildcard directory exemption, normalize-and-compare substitute, or generic `repo-specific` label is enough.

Four classes are pre-approved by D07, with one decision per class and a per-path row in the owning result and A18:

- Repository identity strings: owner/repo slug, clone URL, product name and copyright holders.
- Language-scoped file names: powershell.instructions.md versus terraform.instructions.md and their references.
- Normative guide content and its generated derivatives.
- Metadata lines (Version, Last Updated and .NOTES versions) in a file no convergence PR has touched.

Each row must still show the exact necessary difference and verify that common regions converge. When a convergence PR touches a shared file in both repositories, synchronize its metadata lines so the file converges. Do not preserve stale dates as history in a file being edited. This supersedes D-A02-01's preservation reading for touched files only. Common algorithms, CI security, dependency versions, helper names and harmless wording must converge unless a concrete supported difference is proved. Prefer factoring a shared algorithm with minimal language configuration when that reduces justified mixed-file differences without a new framework.

At A18, refresh both native refs, compare the full tracked union plus historical required-path/capability inventory, inspect every exception and verify refs again. No new unclassified path is allowed. Record equality outside exceptions separately from the raw count of different files. The product comparison is main/main; the intentionally unmerged planning branch is not a product divergence.
