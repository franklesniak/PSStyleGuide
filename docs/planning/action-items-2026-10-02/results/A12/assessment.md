## Finding A12-F01: PS main lacks useful native merge constraints

### Validate

The empty authenticated effective rules permit main updates without platform-enforced PR/check/freshness constraints. This matters independently of the retired automatic writer: current contributors can still merge or push broken generated artifacts, failed policy/lint results, or stale integrations. No negative push drill was attempted against unprotected main.

The useful surviving jobs run for ordinary pull requests in current `build.yml` and `markdownlint.yml`. `verify_generated_artifacts` checks committed generated bytes. `policy` checks workflow contracts. `markdownlint` checks documentation and relevant configured validations. Source plus generator tests remain outcome-owned; a successful check is not a substitute for that acceptance.

### Stakeholders

The owner is both administrator and sole listed maintainer. Contributors need a predictable route through PRs. Guide users and artifact consumers need verified delivered bytes. CI maintainers and dependency maintainers need checks that can be updated without a circular lockout. Security engineers and the accountable owner need clear trust and bypass limits. Reviewers need stable scopes and resolved findings. Incident operators need a precise restoration path. History custodians need old approvals distinguished from current authority. Business/cost stakeholders need low ongoing administration. Windows/Linux developers share these remote rules; no OS-specific setting is required. Privacy, localization and accessibility are not directly changed by branch admission; secrets and accessible documentation remain existing obligations.

## Trust and history limits

Current accepted-base classification prints `MAINTENANCE_REQUIRED` and exits successfully for that class. It identifies necessary review but does not enforce approval. Candidate-owned tests do not supply the missing authority. A03 owns the smallest meaningful admission repair; C is not a disposition accepting that separate loss.

GitHub permits successful, skipped and neutral required-check conclusions. Pinning the app source excludes other check producers but does not pin a workflow file or prevent candidate edits from changing its behavior. Required checks therefore improve ordinary contribution controls without establishing immutable malicious-workflow enforcement. Strict checks add native base freshness; the coordinator must still reassess changed inputs before review/merge acceptance. See [GitHub required-check troubleshooting](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks) and [available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), read 2026-10-02.
