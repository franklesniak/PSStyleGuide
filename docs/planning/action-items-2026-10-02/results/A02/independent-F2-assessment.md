## Distinct options for the canonical decision

1. **Unconditional null-parent current UTC.** Small edit but violates delayed/old finalized new-input semantics. Reject under the existing policy; it cannot score perfect finalization correctness or compatibility.
2. **Stable original PR event time.** A supported, authenticated event context can establish when that event occurred. synchronize establishes publication activity, not necessarily the last author update; opened/reopened/edited are still less equivalent. Freezing the original event solves a rerun clock drift problem but does not solve this semantic mismatch. Do not choose this fallback without an explicit changed policy contract.
3. **Commit author/committer date.** Stable across identical-head reruns but candidate-controlled, permits backdating, and is not proof of finalization. Later unrelated commits complicate per-document interpretation. Reject as authenticated time. Reading the field from an authenticated Git object does not authenticate its claimed time.
4. **Scope-correct local finalization.** Existing staged new documents already produce a worktree difference and current UTC enforcement. Untracked files are outside tracked discovery; they are not a demonstrated null-parent caller defect here. A committed head with no worktree changes is not evidence of a fresh author finalization. An explicit finalization invocation against exact B/H can intentionally validate current UTC at the actual author step, without changing later CI results. This is useful procedural enforcement, not an automatic remote gate.
5. **Explicit supported finalization-date context.** Add a narrowly named CLI input such as -FinalizationUtcDate for exact B/H checks, validate strict real calendar/nonfuture form, reject incompatible invocation modes, and pass it into the existing expected-date comparison for rendered changes. The caller must establish this date at actual finalization and bind it to the same B/H; do not get it from candidate headers, candidate timestamps, current rerun time or an arbitrary PR event. An explicitly selected local finalization mode can supply the existing trusted local clock instead of taking a caller string. Later exact-input validation can reuse the known date. A format-valid argument alone is not authenticated provenance.
6. **Retain endpoint checks with truthful date-proof limits.** Keep stable structural/calendar/nonfuture/baseline comparison when finalization context is absent, and report that exact finalization date was not verified. Do not emit or document full freshness acceptance. If a required automated finalization gate is demanded, missing context must instead be incomplete/failing until a supported producer/caller exists; that is a deliberate operational change, not a helper default. No current workflow caller can truthfully populate an exact date from existing fields alone.
