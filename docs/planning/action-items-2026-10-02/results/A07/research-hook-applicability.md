## Portable compiled-artifact opportunity — ordered decision

**1. Validate and limits.** Research’s `(?i)(^|/)__pycache__/|\.py[cod]$` deliberately catches Windows extension modules and case aliases. Both accepted configurations and the proposed TF configuration lack the fail hook. Both accepted gitignore files and the proposal lack `__pycache__/` and `*.py[cod]`. Active Python tooling and ignored environments do not prevent a force-added compiled artifact elsewhere. Static examples match `module.pyc`, `MODULE.PYC`, `Cache.PYD`, `module.pyo` and `pkg/__PYCACHE__/payload.txt`; near misses `source.py`, `module.pyc.txt` and `pkg/__pycache_notes__/readme.md` do not match. This demonstrates the portable prevention opportunity. No compiled file was added, no actual hook bypass was executed and no current tree is labeled defective. The opportunity remains an A07 follow-up; it does not invalidate the frozen TF66 aggregate.

**2. Stakeholders.** Both maintainers and the scope owner need faithful general safeguards and serial delivery. New contributors need accidental cache ignores and a clear rejection when they force-add platform artifacts; experienced contributors and agents need explicit hook suppression semantics preserved. Windows/Linux Python/tooling maintainers need case aliases and `.pyd` included without rejecting source. Supply/security reviewers and auditors need reviewed source and truthful evidence boundaries; QA needs actual native fail/no-match controls. CI/release operators must distinguish a no-input fail-hook skip from skipped applicable validation. Schedule/cost owners need a finite change after current validation, not a reset. This changes repository admission, not PowerShell/Terraform teaching, generated output, cloud/recovery operations or localization. It is not a secret-scanning guarantee.

**3. Options before scoring.** A: defer the guard and require manual owner review at the first artifact introduction. B: retain the narrow source `language: fail` hook and ignore rules, with coupled finite contract/count evidence. C: add an always-running Python inventory scanner plus ignores. D: integrate rejection into the existing always-running PowerShell validator plus ignores. E: ignores only. F: permanent absence-based exemption/no guard. No change is A with a trigger; F is the unsupported exception variant. A shared configurable runtime framework adds no relevant scope and collapses into C/D with extra cost. Combining B with C/D duplicates one rejection; ignore-plus-rejection is already B/C/D. Restoring every retired suite or publisher does not supply this exact guard.

**4. New rubric.** Scores1–5 measure poor→complete demonstrated fit; totals are judgments. Scope fidelity30: exact artifacts/case paths, not all binaries or Python source. Enforcement25: rejects force-added tracked matches, not only accidental staging. Activation15: actual hook/caller semantics, suppression and applicable counts remain explicit. Supported setup15: no new unpinned runtime/dependencies. Observable verification10: actual failure and near-match cases can distinguish lost controls. Maintenance5: bounded readable change with one owner. Hard constraints: no source-repository writes, blanket absence exemption, dropped existing checks, frozen TF66 input edits, new authority or ignored force-add bypass.
