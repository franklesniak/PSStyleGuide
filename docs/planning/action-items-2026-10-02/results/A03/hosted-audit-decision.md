## Validated root cause

The coordinator inspected native push run37181855158/job111375857602 failing with ERROR, `Hosted audit authority must be the main branch.` The current caller in `markdownlint.yml` always runs `Check-NpmAudit.mjs --ci` after lint for every admitted live push and PR. `hostedAuthorityReference` in that helper requires `refs/heads/main` for push, schedule and manual modes, and a main target base for PRs. D2 broadened workflow events but did not extend this consumer's distinct authority model. The failure is a real integration defect, not a vulnerability result, missing owner permission or a reason to reverse D2.

It affects every newly admitted non-main branch push, both creation and update, and every tag push, including a tag named main. Neither push.before nor the creation flag participates in this audit selector, so D4's new-reference repair does not fix it. A PR targeting a non-main branch also fails before its ordinary-doc applicability check. Main pushes and PRs targeting main retain their intended authority paths; deleted refs are skipped by the caller. Schedule and explicit hosted manual support remain restricted to main. The ordinary command without `--ci` deliberately uses locally fetched origin/main even under dynamic agent environment values; that accepted D40 repair must remain.

There is a second part to the same finding: `ciScope` currently uses `authority.sha` as the PR change base. That is correct only while authority is the actual main target base. If non-main PR authority is obtained from main, keeping this coupling would classify the wrong diff. It could cause unnecessary audits or, when changes cancel differences against main, an incorrect documentation-only exclusion. Exception authority and PR applicability endpoints must be separate identities.

Current tests explicitly expect a topic PR base to be rejected and test scope using a supplied authority as base. They cover the old contract, not the new event-to-audit combination. The all-files aggregate and ordinary current audit therefore passed without proving these hosted contexts. Existing caller tests preserve the audit invocation and failure propagation but do not supply these hosted authority/diff cases. This is not evidence that their other checks failed.

GitHub documents push identity as the pushed tip/ref and PR identity as the synthetic merge commit. Neither a non-main push nor a non-main PR target becomes main risk authority merely because its workflow runs. [GitHub event documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push), [PR event documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request). Git supports fetching an explicit ref from a fixed URL and records the obtained ref/object in FETCH_HEAD. This supports pinning one acquired main snapshot without trusting a local branch name or inventing an event-main SHA. [Git fetch documentation](https://git-scm.com/docs/git-fetch).

## Stakeholders and options before scoring

Risk owners and security reviewers need only accepted main to authorize exceptions; candidate grants, arbitrary target branches and missing authority cannot silently pass. Contributors and the UX owner need branch/tag checks and non-main PRs to work without changing event variables or reconfiguring remotes. QA needs real distinct main/target/head objects and malicious exception proposals, rather than a green main-only unit matrix. CI maintainers need predictable bounded acquisition, clear ERROR versus FINDINGS/PROPOSAL states and no new token or privileged job. Reviewers need exact logged authority and diff identities, including freshness limits. Operational cost matters after correctness and usability; this finding does not introduce customer data or a recovery service.

- N: keep current rejections or defer repair. Existing main behavior is safe but D2's admitted events remain unusable.
- R: restore main-only triggers or skip the audit for other admitted events. This contradicts D2 and bypasses the applicable audit.
- C: allow every event SHA or PR target SHA to supply exceptions. This treats candidate or non-main content as accepted risk authority.
- Z: audit new contexts against empty exceptions. This avoids candidate grants but silently discards legitimate accepted grants and changes proposal comparison semantics.
- M: retain existing exact main-event authority. For newly supported non-main push/PR contexts, acquire main from the reviewed fixed repository URL, pin that commit for exceptions, and use the actual PR target base separately for applicability.
- U: always acquire current main for every hosted context, including existing main events, and separate PR applicability. This is safe with full validation but changes established event-pinned behavior and adds network/freshness churn where the event already provides authority.
- D: use M's authority selection but always audit non-main PRs rather than keep their documentation-only optimization. This is conservative, yet removes a supported contributor behavior and creates avoidable registry dependency for ordinary prose.
- W: obtain main in an additional workflow step and pass an authority SHA to the helper. This can be sound only with authenticated provenance checking; a bare environment override is not authority. It spreads the contract across caller and helper and adds a new handoff.
- J: move the authority/audit logic into a separate trusted central job/service and supply inert candidate data. This can enforce stronger execution separation, but needs new orchestration and is not necessary for the selected procedural-maintenance model.

M combined with separate applicability is one coherent remedy, not two optional fixes. M plus always-audit is D. M plus a workflow-produced authority is W; M plus a new service is J. Adding a stale local-origin/main fallback to M changes its safety contract and is ineligible. Reusing arbitrary target-base exceptions or passing a hard-coded release SHA are not safe smaller repairs. Restoring vulnerable packages, swallowing ERROR, excluding the audit step or using `continue-on-error` are ineligible. No useful additional combination removes the need to distinguish authority from applicability.
